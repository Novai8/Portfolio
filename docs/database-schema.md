# Supabase Case Schema

Table: `cases`

| Column | Purpose |
|---|---|
| `id` | UUID primary key generated by Supabase |
| `case_number` | Case identifier |
| `report_number` | Report identifier |
| `customer_name` | Customer name from sample data |
| `queue` | Review queue |
| `report_type` | Type of report |
| `submission_date` | Submission date |
| `quality_issues` | Identified quality problems |
| `missing_information` | Missing information |
| `invoice_status` | Invoice verification state |
| `customer_requirements` | Requirements relevant to the review |
| `deadline` | Required completion date |
| `urgency` | Review urgency |
| `recommended_action` | Suggested next action |
| `email_required` | Whether clarification is required |
| `email_status` | Follow-up email state |
| `overall_status` | Business outcome |
| `gmail_message_id` | Original Gmail message ID |
| `processing_status` | Workflow processing state |
| `document_status` | Supporting document state |

## Status values

### `processing_status`

`Received`, `Under Review`, `Reviewed`, `Email Sent`, `Completed`, `Failed`

### `email_status`

`Not Required`, `Pending`, `Sent`, `Failed`

### `overall_status`

`Ready`, `Needs Review`, `Missing Information`, `Escalation Required`

### `document_status`

`Complete`, `Missing Documents`, `Needs Review`, `Not Applicable`

### `invoice_status`

`Present`, `Missing`, `Inconsistent`, `Not Applicable`, `Unable to Verify`

## Data integrity rules

- `id` is generated by Supabase rather than supplied by the workflow.
- `gmail_message_id` must come directly from Gmail.
- Review fields should reflect available evidence only.
- Missing or contradictory information must remain explicit rather than being guessed.
